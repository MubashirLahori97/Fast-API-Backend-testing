# 10.1 Contact the Support Team & Consult With Support Team: decisions

Built in `app/support/` on 5 Nov 2026, against Client story 10.1 and the Super Admin stories that receive the requests (5.1 Manage Support Requests, 6.3 Knowledge Gaps, 11.1 Notifications, 2.1's Needs Attention strip). No tests or migration yet (see the end).

## Design choices

- **One table, `support_requests`,** for every kind the team's list shows that 10.1 creates. Stored codes:
  - `kind`: `talk_to_support` (Talk to Support Team), `consultation` (Consultation Request), `knowledge_gap` (Knowledge Gap);
  - `source`: `form` or `conversation`. Check constraints keep a consultation to `form` and a knowledge gap to `conversation`;
  - `status`: `open` or `resolved`, with `resolved_at` set exactly when resolved, and `resolved_by_id`.
- **Two routes, one body.** The body is `{client_request_id, kind, message}` with `kind` `talk_to_support` or `consultation`. A request about a profile goes to `/profiles/{profile_id}/support-requests`, so the profile comes through `OwnedProfile` like everywhere else (another account's profile gets the same 404). Any owned profile is accepted, including a turned-off member or one with a pending deletion, since that's often why the client writes. `/support-requests` is only for a client with no profile yet. It doesn't guess one.
- **Resends.** The app makes `client_request_id` once per request and sends it again with any retry, including a request it kept while offline. A resend answers 200 with the saved request, and no second email. There's a unique key on `(account_id, client_request_id)`, and the account row is locked `FOR UPDATE` while sending, so the resend check and the hourly limit hold under parallel requests.
- **From a conversation.** `create_from_conversation` copies a client message into the request:
  - by default, the one the Oracle's latest reply answers (the question it couldn't answer, or "Can I talk to someone?"); the caller can pass `message_id` instead;
  - sending the same message twice returns the first request (partial unique index on `source_message_id, kind`, inserted in a savepoint);
  - it adds the request, its job and its audit event to the session and **doesn't commit**: the conversations package commits them with its own changes;
  - it refuses (409 `not_sendable`) unless the message's safety check came back `none`. Story 10.1: an emergency, crisis or urgent concern gets the safety path and an escalation, never a support request. An unchecked message is refused too;
  - it refuses a conversation that's deleted or isn't this profile's (404), and a profile that can't be used (`check_can_use`).
- **The message is copied,** so the request stays readable if the conversation is deleted or purged. `conversation_id` and `source_message_id` become null when those rows go.
- **Health data.** The message and the team's `internal_notes` are health data:
  - plain text until Phase 4's field encryption, like the other health fields;
  - never logged, audited, emailed or put in job payloads.
- **Audit events** hold the kind and the request's id only: `support.request_sent` (actor: the client), and for the team `support.request_viewed`, `support.request_note_saved`, `support.request_resolved` and `support.request_reopened` (Super Admin 5.1: every view, note and status change). Opening a request counts as a view; loading the list doesn't.
- **The team email.** The `support.notify_team` job (payload: the request id) is due at once, and the worker polls every 2 seconds, so the email goes out well within 1 minute:
  - it says "You have a new support request to review" with the type, the request id and the time received, and no client name, email, profile or message (Super Admin 11.1: emails never include health information or client names);
  - `team_notified_at` records when it went, and stops a second send;
  - in production `get_email_sender` refuses to run until a provider exists, so the job fails and is retried (5 tries).
- **The client's details aren't copied.** First name, email and account type are read from the account when the team opens the request, so they're current. The profile is a foreign key with `ON DELETE SET NULL`: when a family member's data is deleted, the request no longer says who it was about, and no copy of their name is left.
- **Deleted with the account.** `account_id` is `ON DELETE CASCADE`, so the message doesn't outlive the account. The audit events (kind and id) stay.
- **Teens.** A teen with their own account can contact the team, but a consultation is refused (403). `is_teen_account` is "has a date of birth and is under the age of majority": sign-up refuses anyone younger, so only Phase 3b's invited teens match. Phase 3b can swap in its own marker.
- **No client history endpoint.** Story 10.1 never shows the client their past requests or their status (the team replies by email), so there's no `GET` for clients.
- **Not gated by the plan.** Story 9.1's list of greyed-out features doesn't include contacting the team or consultations, so both work during the trial and after it ends (question 3 below).
- **Rate limit.** Every request emails the team, so each account can send `max_support_requests_per_hour` (10) an hour, counted from `support_requests` (`ix_support_requests_account_created`). It applies to conversation requests too.
- **The team's side** (for Phase A, no endpoints yet):
  - every function takes the admin `User` and refuses anyone whose role isn't `admin` or `super_admin`, as a second check behind Phase A's sign-in dependency;
  - the list puts open requests first, oldest first. It searches first name or email, and filters by kind, status, account type (adult or teen, the same rule as `is_teen_account`) and date received;
  - resolving a resolved request, or reopening an open one, changes nothing and records nothing. Reopening clears `resolved_at` and `resolved_by_id`; the audit log keeps the history;
  - notes are one free-text field that each save replaces, as 5.1 describes. The Phase A endpoint's schema limits its length;
  - `open_counts` gives open requests by kind, for the Needs Attention strip.

## Messages

From the stories:

- empty message: "Please tell us how we can help.". It's used for the Consult form as well, whose field is "What would you like help with?", because 10.1 has only this one empty-message text;
- the contact form is sent: "Thanks, your message has been sent. The support team will reply by email within one business day.";
- a consultation is sent: "Thanks, the support team will get in touch by email to talk about the next steps.";
- sent from a conversation: "I’ve let the support team know. They’ll get back to you by email within one business day.", returned as `message` for the conversations package to show;
- a database error while sending: "We couldn’t send your message just now. Please try again." (503 `send_failed`);
- the team's confirmations (Super Admin 5.1): "This request has been marked as resolved.", "This request has been reopened.", "Your note has been saved."; a database error there gets "We couldn’t do that just now. Please try again.".

Not in the stories:

| Situation | Code | Message |
| --- | --- | --- |
| Message over the length limit | `validation_error` (422) | "That message is too long. Please keep it to 5,000 characters or fewer." (worded like the chat limit) |
| Too many requests in an hour | `too_many_support_requests` (429) | "You’ve sent a lot of messages to the support team in the last hour. Please try again later." |
| A teen account asks for a consultation (the app hides the option) | `consultation_not_available` (403) | "Consult with support team isn’t available on a teen account." |
| From a conversation: the message isn't safe to send, or wasn't checked | `not_sendable` (409) | "This message can’t be sent to the support team." |
| From a conversation: message not found | `message_not_found` (404) | "We couldn’t find that message." (the conversations package's text) |
| From a conversation: conversation not found | `conversation_not_found` (404) | "We couldn’t find that conversation." (same) |
| Profile not found, or another account's | `profile_not_found` (404) | "We couldn’t find that profile." (same as `OwnedProfile`) |
| Team side: unknown request | `support_request_not_found` (404) | "We couldn’t find that request." |
| Team side: not an admin | `not_allowed` (403) | "Only the support team can do that." |
| The team email | | Subject "New support request: [Type]"; the body names the type, id and time, and says the details are in the admin panel |

## Open questions for the BA

1. **"Talk to the Support Team, with the Client's message" from a conversation:** is that the message where the client asked for a person, or something they write after agreeing? Built: the message the Oracle's offer answered, or any client message the conversations package names.
2. **Knowledge gaps (Super Admin 6.3):** the gap listing groups similar questions, with a topic and its own status (New, Answered, Dismissed), and never shows the client. Built: only the Knowledge Gap support request; Phase A3 builds the gap listing from these with the AI team. When the client deletes their account, should the question stay as a gap? It's the client's own words and may hold health information.
3. **Consultations during the trial:** 4.1 greys out the dashboard's other widgets during the trial, which would include the Consult card, but 9.1's greyed-out list doesn't mention consultations, and Profile & Account isn't greyed out. Built: allowed during and after the trial. Which is right?
4. **The client's own requests:** should the client see past requests or their status anywhere, the way 11.1 shows "Email change requested"? Built: no.
5. **Who gets the email:** one shared support address, or each Admin and the Super Admin according to their notification preferences (Super Admin 11.1)? Built: one address now; Phase A adds the per-admin preferences and the in-app bell.
6. **Account deletion:** requests are deleted with the account (the audit events stay). Is that right, or must the team's record of a request be kept like the escalations (question 27)?
7. **The in-app reminder** when a client doesn't reply to the team's email (10.1's alternate scenario): what does it say, and is it sent by the team by hand? It's left for Phase A with Phase 9's notifications.

## For other parts of the build

- **Conversations and the Oracle contract:** the Oracle needs a way to say "offer to send this to the support team", either as a knowledge gap or as a request for a person (a widget or a flag in `app/oracle/contract.py`). Then the conversations package calls `create_from_conversation` when the client agrees, before saving the reply to their "yes", and shows the result's `message`. It shouldn't offer while a safety hold is open; the safety-level check refuses unsafe messages anyway.
- **11.1 email change requests** belong in the same team list (Super Admin 5.1). If 11.1 stores them in `support_requests`, add `email_change` to `ck_support_requests_kind` and to `Kind`, plus a `requested_email` column; otherwise Phase A's list combines both tables.
- **Phase 4** encrypts `support_requests.message` and `internal_notes` with the other health fields.
- **Phase 3b** may replace `is_teen_account` with an explicit teen-account marker.

## The migration

There's one new table, `support_requests`. Autogenerate should produce it whole. Check that `create_table` lists the 8 check constraints and the unique key, and that the partial unique index `uq_support_requests_source_message_kind` keeps its `postgresql_where`. Nothing changes on existing tables, and there are no seed rows, data changes or triggers.
